# Rasputin Maintainer Handoff

This is the practical entry point for an engineer inheriting Rasputin. It
describes what is source, what is local state, where behavior lives, and which
checks establish a trustworthy starting point. When this guide disagrees with
the implementation or a passing test, the implementation wins and this guide
must be corrected in the same change.

## First 90 minutes

1. Read [`CODEX_ONBOARDING.md`](CODEX_ONBOARDING.md) for build commands and hard rules.
2. Read [`../THREAT_MODEL.md`](../THREAT_MODEL.md) before changing tools, approvals,
   authentication, workspaces, model execution, or unattended behavior.
3. Read [`README.md`](README.md) to identify the current contract, active plan,
   and historical documents relevant to the task.
4. Check `git status --short` and `git branch --show-current`. Do not discard or
   absorb an existing dirty worktree into unrelated work.
5. Run the tracked-file maintenance audit:

   ```powershell
   .\.venv\Scripts\python.exe scripts\audit_repository.py
   ```

6. Establish the relevant verification baseline. Backend, frontend,
   documentation, and live UI checks are separate evidence boundaries; passing
   one does not prove the others.

## What belongs in a handoff

The handoff artifact is a clean Git clone plus any separately documented
secrets or operator procedures. It is not a copy of the working directory.

| Include | Regenerate or keep local |
| --- | --- |
| `backend/`, `frontend-src/`, `scripts/`, `tests/` | `.venv/`, `node_modules/` |
| `desktop/`, deployment configuration, runtime manifests | `frontend/`, `build/`, `dist/` |
| Current contracts and maintainer documentation | `.worktrees/`, caches, test reports |
| `.env.example` and documented configuration names | `.env`, credentials, certificates, model weights |
| Empty tracked placeholders such as `workspace/.gitkeep` | `workspace/`, `data/`, `testdata/`, local databases |

The repository safety check enforces the most important version-control
boundary:

```powershell
npm.cmd run checkRepoSafety
```

## Ownership map

| Area | Primary responsibility | Start reading |
| --- | --- | --- |
| HTTP and authentication | Request validation, owner/admin boundaries, API contracts | `backend/api/`, `backend/core/auth.py` |
| Agent execution | Budgets, tool loop, failure state, test-and-repair loop | `backend/engine/agent.py` |
| Model lifecycle | Catalog, compatibility, acquisition, providers, load profiles | `backend/models/` |
| WarSat | Hardware discovery, placement, deployment, runtime lifecycle | `backend/warsat/` |
| Governed tools | Filesystem, Git, shell, MCP discovery, approvals | `backend/mcp/`, `backend/tools/` |
| Durable user state | Workspaces, sessions, memory, RAG, runtime stores | `backend/core/`, `backend/rag/` |
| Workstation UI | Routing, application state, feature views and primitives | `frontend-src/src/` |
| Desktop distribution | Electron lifecycle, packaged backend, installer | `desktop/`, `scripts/*desktop*` |
| Verification | Unit, contract, Playwright, certification, release gates | `tests/`, `scripts/verify_*`, `scripts/certify_*` |

## Source and state boundaries

- `frontend-src/` is editable source; `frontend/` is generated by Vite and is ignored.
- Native tests must use an isolated `RASPUTIN_DATA_DIR`. Never point tests at an
  owner's actual native or Docker data.
- Models, runtime databases, generated reports, and credentials are operational
  state, not repository content.
- The Docker service on port 8787 may be the owner's real instance. Local
  verification uses an isolated data directory and the documented development port.
- A model being deployed does not prove chat, streaming, tool use, or coding-mode readiness.

## Current maintenance baseline

The 2026-08-28 tracked-file audit found roughly 210 owned source/tooling files and
approximately 89,000 lines. The repository is organized by feature, but maintenance
risk is concentrated in a small number of oversized files rather than spread
uniformly across the tree.

Work through these boundaries in this order:

1. Split `frontend-src/src/styles/rasputin.css` by feature without changing the
   rendered interface, following [`CSS_OWNERSHIP.md`](CSS_OWNERSHIP.md).
2. Extract routing and orchestration responsibilities from
   `frontend-src/src/app/App.jsx`.
3. Split model-library and WarSat views by workflow/tab.
4. Separate WarSat probing, planning, validation, deployment, and lifecycle code.
5. Extract governed-chat policy and tool-loop state transitions from the agent runtime.
6. Divide `tests/testBackendSmoke.py` into feature-owned suites while preserving discovery.

Run `scripts/audit_repository.py` after each slice. File length is a diagnostic,
not a design goal: a cohesive large module is preferable to arbitrary fragments,
but ordinary modules should trend below 500 lines and functions below 100 lines.

## Commenting standard

Comment the whole owned codebase by documenting boundaries, not by translating
syntax into English.

- Every owned module gets a short purpose and ownership header.
- Public Python classes/functions and exported JavaScript contracts get docstrings
  or JSDoc describing inputs, outputs, side effects, and failure behavior.
- Inline comments explain security decisions, owner scoping, approval boundaries,
  concurrency, retries, GPU placement, compatibility workarounds, and invariants.
- CSS gets feature/ownership section headers and dependency notes, not a comment
  above every selector.
- Tests use descriptive names; comments explain only non-obvious setup or the
  regression being protected.
- Do not document a boundary immediately before a planned split. Stabilize it,
  then document its resulting contract.

Initial targets are 100% module-purpose coverage, at least 80% documented public
Python APIs, and at least 80% documented exported JavaScript contracts. Exceptions
must be explicit rather than silently lowering the target.

## Definition of handoff-ready

Rasputin is ready to transfer when an engineer unfamiliar with the project can:

1. Install dependencies and build from a clean clone.
2. Run the relevant backend, frontend, documentation, and safety checks.
3. Explain the security and runtime boundaries from current documentation.
4. Locate the owner of a UI workflow and its backend contract.
5. Make and verify one frontend change and one backend change without oral guidance.
6. Diagnose one failed agent or WarSat operation using logs, state, and documented next steps.

Record anything that still requires oral history as a documentation or
architecture defect; do not make private knowledge part of the operating model.
